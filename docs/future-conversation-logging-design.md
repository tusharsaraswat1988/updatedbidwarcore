# BIDWAR WhatsApp AI — Future Intelligent Conversation Logging Design Note

> **Status:** Conceptual Architecture & Design Specification (Documentation Only)  
> **Phase:** Future Implementation Phase  
> **Scope:** Structured conversation intelligence, privacy boundaries, and analytics extraction for BIDWAR WhatsApp assistant interactions.

---

## 1. Executive Objective

The purpose of the Future Intelligent Conversation Logging system is to capture structured conversational signals from user interactions to enable:
1. Operations team visibility into unresolved tournament questions.
2. Analytics on popular features, tournament sports formats, and pricing queries.
3. Proactive customer success for frustrated or blocked organizers.
4. Continuous evaluation of AI understanding without leaking private personally identifiable information (PII).

---

## 2. Fundamental Architectural Rule: Separating Facts from AI Inferences

A critical pitfall in conversational analytics is conflating **objective facts** (deterministic backend events) with **probabilistic AI inferences** (model predictions).

Future logging schemas MUST strictly separate:

| Category | Definition | Examples |
| :--- | :--- | :--- |
| **Objective Facts (Deterministic)** | Ground-truth metadata verifiable from database records, system logs, or exact verbatim user inputs. | • User mobile phone number<br>• Verified member ID<br>• Explicit command executed (`STOP`, `OPTIN`, `BPL`)<br>• Database update executed (`membersTable` updated)<br>• Timestamp of message receipt<br>• Message delivery status from WhatsApp provider |
| **AI Inferences (Probabilistic)** | Predictions, classifications, or estimates generated by Gemini or NLP classifiers. Must always be tagged with confidence scores. | • Inferred intent: `intent_name_change` (conf: 0.95)<br>• Inferred sentiment: `possible_frustration_detected` (conf: 0.88)<br>• Inferred topic: `auction_operator_console`<br>• Inferred language: `hinglish` |

### Invariant:
**An inference must never be written into an authoritative transactional table as a verified fact.**
For example: `"Possible frustration detected"` is an inference stored in conversational analytics, NOT a verified support ticket or account flag.

## 3. Proposed Future Schema (Conceptual)

```sql
-- Conceptual future table for structured conversation analytics
CREATE TABLE conversation_intelligence_logs (
    id BIGSERIAL PRIMARY KEY,
    session_id VARCHAR(64) NOT NULL,
    message_id VARCHAR(128) NOT NULL UNIQUE,
    recipient_mobile_hash VARCHAR(64) NOT NULL, -- SHA-256 pseudonymized hash for GDPR/privacy
    verified_identity_kind VARCHAR(32) NOT NULL, -- "guest" | "member" | "licensed_organizer" | "trial_organizer"
    verified_member_id VARCHAR(64),
    
    -- DETERMINISTIC FACTS
    channel VARCHAR(16) NOT NULL DEFAULT 'whatsapp',
    explicit_language_preference VARCHAR(16), -- 'hindi' | 'english' | 'hinglish' (only if explicitly set by user)
    request_status VARCHAR(32) NOT NULL,      -- 'handled_deterministic' | 'handled_ai' | 'handed_off_human' | 'failed_fallback'
    action_executed VARCHAR(64),              -- e.g., 'profile_name_update', 'wa_opt_out', 'none'
    database_mutation_succeeded BOOLEAN,
    
    -- PROBABILISTIC AI INFERENCES (JSONB)
    ai_inferences JSONB DEFAULT '{
        "primary_intent": null,
        "intent_confidence": null,
        "detected_topic": null,
        "unresolved_issue": false,
        "follow_up_required": false,
        "conversational_signals": []
    }'::jsonb,
    
    -- UNRESOLVED & FOLLOW-UP FLAGS
    unresolved_summary TEXT,                  -- Short, non-PII summary of question that could not be answered
    follow_up_assigned_role VARCHAR(32),      -- 'tournament_ops' | 'technical_support' | 'sales'
    
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX ix_comm_intel_logs_created_at ON conversation_intelligence_logs(created_at);
CREATE INDEX ix_comm_intel_logs_unresolved ON conversation_intelligence_logs((ai_inferences->>'unresolved_issue'));
```

## 4. Signal Extraction Specification

### A. User Intent
Extracted intents must categorize the primary objective of the message:
- `FAQ_PRODUCT_OVERVIEW`: Inquiries about what BidWar is.
- `FAQ_PRICING`: Inquiries about per-tournament license tiers.
- `AUCTION_OPERATOR_HELP`: Questions about running the live bidding console.
- `SCORING_MATCH_SETUP`: Questions about cricket/badminton match scoring.
- `PROFILE_MODIFICATION`: Requests to change name, phone, or account details.
- `HUMAN_ESCALATION`: Direct requests for human agent or phone call.
- `COMPLAINT_OR_DISAPPOINTMENT`: Negative feedback on usability or platform performance.
- `GENERAL_CONVERSATION`: Greetings, acknowledgements, or pleasantries.

### B. Topic Hierarchy
- `Auction` -> `Operator Console` | `Mobile Bidding` | `Stage LED` | `OBS Overlay` | `Fortune Wheel`
- `Scoring` -> `Cricket` (DLS, balls, overs) | `Badminton` (sets, points, rotation)
- `Tournament` -> `Creation` | `Teams Roster` | `Player Registration`
- `Pricing & Licensing` -> `Starter` | `Pro` | `Elite` | `Free Trial`
- `Account & Access` -> `Name Change` | `Login` | `Consent/STOP`

### C. Explicit Language Preference
- Only logged when user explicitly requests a language (e.g. "Talk in Hindi" or "Ab English mein explain karo").
- If the user merely uses mixed words without an explicit request, it is categorized as `inferred_language: 'hinglish'`, NOT an explicit preference.

### D. Request Status
- `RESOLVED`: User's question was answered authoritatively within knowledgebase boundaries.
- `UNRESOLVED`: Question was outside approved boundaries (e.g., custom unlisted pricing or proprietary code) and redirected to support.
- `HANDED_OFF`: Explicit handoff card with support contact details delivered.
- `MUTATED`: Controlled backend database update executed after verification.
- `REVOKED`: Universal consent revocation executed (`STOP` / `DECLINE`).

### E. Unresolved Issues & Required Follow-Up
When a user asks a question that neither Gemini nor deterministic commands can answer:
- The system flags `unresolved_issue: true`.
- An operations follow-up ticket is staged with:
  - Context of inquiry (e.g., "Organizer requested custom 40-team corporate tournament pricing").
  - Target channel: `whatsapp_callback` or `phone_call`.
  - Priority: `P1` (if tournament date is within 48h) or `P2` (general inquiry).

### F. Optional Non-Sensitive Conversational Signals
- `frustration_signal`: User expressed annoyance or repeated error reports.
- `confusion_signal`: User asked multiple clarification questions in succession.
- `urgency_signal`: User mentioned tight timeline ("auction starts today").
- `appreciation_signal`: User expressed satisfaction ("thanks ho gaya").

**Prohibited Signals (MUST NEVER BE INFERRED OR STORED):**
- Age, gender, religion, political beliefs, geographic stereotypes, or socio-economic profiling.
- Raw credit card details, UPI PINs, passwords, or personal identity numbers.

## 5. Privacy, Data Retention, & WhatsApp Compliance

1. **Zero Raw Token Archiving**:
   Full unredacted chat transcripts should not be retained indefinitely in raw format. After a 30-day retention window, raw text should be purged, retaining only the structured signals and anonymized metrics.
2. **Pseudonymization**:
   Mobile numbers in the analytics warehouse must be stored as one-way HMAC-SHA256 hashes using a server secret salt.
3. **Consent Enforcement**:
   If a user sends `STOP` or `UNSUBSCRIBE`, their contact state in `waConsentEventsTable` is updated immediately. Future analytics jobs must respect opt-out boundaries.

---

## 6. Implementation Readiness

This design requires **zero new database migrations** for the current conversational intelligence upgrade. All current fixes leverage the existing `botSessionsTable` JSON payload, strictly preserving backwards compatibility and system performance.
